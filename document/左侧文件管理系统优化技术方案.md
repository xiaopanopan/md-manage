# md-manage 左侧文件管理系统优化技术方案

> 文档状态：规划建议
>
> 调研日期：2026-08-03
>
> 适用分支：`feature/tauri-migration`
>
> 实施状态：尚未实施，本文用于后续重构与验收

## 1. 文档目标

本文统一定义左侧文件管理系统的状态模型、文件排序、新建位置、取消选择、拖拽移动和操作反馈，解决当前实现中以下问题：

1. “正在编辑的文件”和“文件树选中项”共用 `currentFile`，无法安全取消选择；
2. 工具栏新建位置由当前打开文件的父目录隐式决定，用户难以预测；
3. 文件树当前按修改时间混排，保存文件后列表会跳动；
4. 拖拽只表达“移动”，但放置范围和目标反馈不够明确；
5. 新建文件夹后没有选中、展开和滚动定位，容易让用户误以为创建失败；
6. 文件系统层、状态层和展示层之间缺少统一的排序与选择约定。

本文参考 VS Code Explorer 的成熟行为，但不会机械照搬。md-manage 是以 Markdown 知识目录为核心的单工作区应用，应优先保证目录稳定、操作可预测和内容安全。

## 3. VS Code Explorer 行为调研

### 3.1 排序模式

VS Code 的 `explorer.sortOrder` 提供以下模式：

| 模式 | 官方行为 |
|---|---|
| `default` | 按名称排序，文件夹在文件之前 |
| `mixed` | 文件和文件夹按名称混排 |
| `filesFirst` | 按名称排序，文件在文件夹之前 |
| `type` | 文件按扩展名分组后按名称排序，文件夹优先 |
| `modified` | 按最后修改时间倒序，文件夹优先 |
| `foldersNestsFiles` | 文件夹优先，具有嵌套子文件的文件排在其他文件之前 |

VS Code 默认使用 `default`，说明通用文件管理器首先追求目录位置稳定，而不是把最近修改项不断移动到顶部。

此外，VS Code 还提供：

- `explorer.sortOrderReverse`：反转排序；
- `explorer.sortOrderLexicographicOptions`：控制大小写混排、大写优先、小写优先或 Unicode 顺序；
- 修改时间相同时回退到名称排序，确保结果稳定。

### 3.2 自然语言和数字排序

VS Code 不直接使用简单的字符串 `<` 比较，而是复用 `Intl.Collator`：

```ts
Intl.Collator(undefined, { numeric: true })
```

核心效果：

- `笔记2.md` 排在 `笔记10.md` 前；
- 名称按当前系统语言环境比较；
- 对比较结果相同但原始字符串不同的情况再次消歧，避免排序不稳定；
- 扩展名排序先比较扩展名，再比较完整文件名。

### 3.3 自动定位

VS Code 的 `explorer.autoReveal` 默认为 `true`：打开文件时自动在文件树中展开、定位并选中对应文件；也支持只聚焦不滚动和完全关闭。

这表明“新建或打开成功后可见”是文件管理器的重要反馈，不能只刷新数据。

### 3.4 拖拽、确认和撤销

VS Code 官方默认：

- `explorer.enableDragAndDrop = true`；
- `explorer.confirmDragAndDrop = true`；
- `explorer.enableUndo = true`；
- 删除操作默认需要确认；
- 文件操作可进入统一的 undo/redo 链路。

其设计重点不是阻止移动，而是让可能产生较大影响的文件操作可确认、可恢复。

### 3.5 紧凑目录和文件嵌套

VS Code 支持：

- `explorer.compactFolders`：把连续单子目录压缩成一个树节点；
- `explorer.fileNesting.enabled`：把源码、类型声明、映射文件和锁文件等关联项嵌套显示。

这两项主要服务代码工程。md-manage 的目录本身承载知识分类语义，压缩目录会隐藏层级，文件嵌套对纯 Markdown 工作区收益也很低，因此第一阶段不建议实现。

### 3.6 对 md-manage 的取舍

| VS Code 能力 | md-manage 决策 | 原因 |
|---|---|---|
| 文件夹优先、名称自然排序 | 采用并作为默认 | 顺序稳定，符合通用文件管理认知 |
| 修改时间、扩展名排序 | 精简后采用 | 满足不同工作方式，但不作为默认 |
| 文件和文件夹混排、文件优先 | 首期不提供 | 增加设置复杂度，对 Markdown 目录收益低 |
| 自动展开、定位和选中 | 采用 | 新建、打开、移动结果必须可见 |
| 拖拽确认 | 撤销完成前采用 | 当前移动属于立即生效的真实文件操作 |
| 文件操作撤销 | 分阶段采用 | 能显著降低误移动和误重命名风险 |
| 紧凑目录 | 不采用 | 知识目录的中间层级具有业务语义 |
| 文件嵌套 | 不采用 | Markdown 工作区缺少源码伴生文件场景 |

## 4. 当前实现评估

### 4.1 已合理的能力

当前实现具备以下正确基础：

- Tauri Rust 命令统一校验工作区边界；
- 新建名称拒绝 `/`、`\\`、空名称和保留名称；
- Markdown 文件自动补充 `.md`；
- 新建、移动和重命名拒绝覆盖同名目标；
- 文件夹不能移动到自身或自身子目录；
- 移动正在编辑的文件或其父目录前会先保存；
- 移动、重命名后会同步更新 `currentFile` 和 `recentFiles`；
- 删除进入系统废纸篓，而不是直接永久删除。

这些安全能力应保留，不应在 UI 重构时下放到 React。

### 4.2 当前排序问题

Rust `list_dir` 当前执行：

```rust
nodes.sort_by(|a, b| b.modified_at.cmp(&a.modified_at));
```

由此产生：

1. 文件夹和文件混合排序；
2. 保存 Markdown 后项目立即跳位；
3. watcher 刷新会改变用户刚刚形成的位置记忆；
4. 修改时间使用字符串比较，虽然 RFC 3339 通常可排序，但不应承担展示规则；
5. 用户无法切换为名称、类型等常见排序模式。

### 4.3 当前选择模型问题

`FileItem` 使用 `currentFile === file.path` 作为文件树激活状态。这使一个字段同时承担：

- 编辑器当前文档；
- 文件树视觉选择；
- 全局重命名和删除目标；
- 工具栏新建位置推导依据。

因此，如果直接把 `currentFile` 清空来实现取消选择，会关闭右侧文档并破坏编辑连续性。

### 4.4 当前新建位置问题

工具栏新建当前使用：

```ts
const activeDir = currentFile
  ? findFile(files, currentFile)?.parentPath ?? workspace
  : workspace;
```

这意味着用户即使正在浏览另一个目录，新文件仍可能被创建到正在编辑文件的父目录。目标规则不可见，也无法通过点击侧栏空白恢复到工作区根目录。

右键菜单规则相对合理：

- 右键文件夹：创建到该文件夹内部；
- 右键文件：创建到文件所在目录。

### 4.5 当前拖拽问题

当前拖拽的底层移动和路径保护基本正确，但展示层存在问题：

- 文件夹的整个递归容器都是放置区，而不仅是文件夹行；
- 拖到文件行时，事件可能由最近的父文件夹接收；
- 用户看不到明确的“将移动到哪个目录”；
- 同目录移动静默无结果；
- 折叠文件夹不会在悬停时自动展开；
- 移动成功后没有 toast、撤销或定位；
- 当前文件树没有手工排序元数据，因此拖拽只能表示目录移动，不能表示列表排序。

## 5. 目标产品规则

### 5.1 状态模型拆分

建议增加独立的 Explorer 状态：

```ts
type ExplorerSelection = {
  path: string;
  kind: 'file' | 'folder';
} | null;

interface ExplorerState {
  selectedEntry: ExplorerSelection;
  expandedPaths: string[];
  sortMode: 'name' | 'modified' | 'type';
  sortDirection: 'asc' | 'desc';
}
```

职责划分：

| 状态 | 职责 |
|---|---|
| `currentFile` | 右侧编辑器当前打开的文档 |
| `selectedEntry` | 文件树当前操作对象和创建位置依据 |
| `expandedPaths` | 文件夹展开状态 |
| `sortMode` | 文件树展示排序方式 |
| `sortDirection` | 当前排序方向 |

`selectedEntry` 不建议跨应用重启持久化；`sortMode` 和 `sortDirection` 可存入现有 Zustand persist。展开状态可按工作区保存，也可在第一阶段仅保留当前会话。

### 5.2 选择与取消选择

推荐交互：

1. 单击文件：设置 `selectedEntry`，并通过 `openDocument` 打开文件；
2. 单击文件夹行：设置 `selectedEntry`，同时展开或折叠；
3. 单击展开箭头：只切换展开状态，不改变当前文档；
4. 单击文件树空白：把 `selectedEntry` 设为 `null`；
5. 按 Escape：清除 `selectedEntry`；
6. 取消选择后，`currentFile` 和编辑器内容保持不变；
7. 不建议再次点击已选文件切换为未选，避免和重新聚焦混淆。

视觉上应区分：

- **选中项**：用于新建、移动、删除、重命名的实底背景；
- **已打开文件**：当它不是选中项时，使用左侧细线、圆点或弱强调标识。

### 5.3 新建位置解析规则

所有工具栏新建必须通过一个纯函数解析目标：

```ts
function resolveCreateTarget(
  workspace: string,
  selection: ExplorerSelection,
  fileIndex: Map<string, FileNode>
): string;
```

统一规则：

| 操作上下文 | 新建位置 |
|---|---|
| 选中文件夹后点击工具栏 | 该文件夹内部 |
| 选中 Markdown 文件后点击工具栏 | 该文件所在目录 |
| 没有选择项 | 工作区根目录 |
| 右键文件夹选择新建 | 该文件夹内部 |
| 右键文件选择新建 | 该文件所在目录 |
| 在侧栏空白处右键新建 | 工作区根目录 |

创建弹窗必须显示相对目标路径，例如：

```text
新建 Markdown 文件
位置：document/design
```

创建完成后的反馈：

- 新建文件：展开父目录、滚动定位、选中并打开；
- 新建文件夹：展开父目录、滚动定位并选中新目录；
- 创建在折叠目录中时必须自动展开；
- 创建失败时展示后端错误类型，而不是全部归为“名称可能不可用”。

默认名称发生冲突时，可借鉴增量命名：

```text
untitled.md
untitled 2.md
untitled 3.md

新文件夹
新文件夹 2
新文件夹 3
```

用户主动输入的名称如果冲突，应明确提示并保留输入，不应静默覆盖。

### 5.4 文件展示顺序规范

#### 默认规则

md-manage 默认采用：

1. 文件夹优先；
2. 文件夹内部按名称自然升序；
3. 文件按名称自然升序；
4. 数字采用数值语义；
5. 比较结果相同时使用原始完整名称，再使用完整路径消歧；
6. 每一级目录独立递归排序。

示例：

```text
📁 archive
📁 document
📁 notes2
📁 notes10
📄 README.md
📄 笔记2.md
📄 笔记10.md
```

#### 可选模式

第一阶段只提供三种模式，避免设置膨胀：

| 模式 | 规则 |
|---|---|
| 名称 | 文件夹优先，各组按自然名称排序；默认升序 |
| 最近修改 | 文件夹优先，各组按修改时间倒序；时间相同回退到名称 |
| 类型 | 文件夹优先；文件按扩展名、完整名称排序 |

排序方向只反转组内顺序，**不反转“文件夹优先”**。这与 VS Code 的完全 comparator 反转略有不同，但能保持 Markdown 目录稳定。

不建议首期提供：

- 文件优先；
- 文件夹和文件混排；
- 手工排序；
- 创建时间排序，因为跨平台创建时间语义不一致。

#### 自然排序比较器

排序属于展示策略，应在 TypeScript 展示层实现：

```ts
const fileNameCollator = new Intl.Collator(undefined, {
  numeric: true,
  sensitivity: 'base',
});

function compareNames(a: string, b: string): number {
  return fileNameCollator.compare(a, b)
    || (a < b ? -1 : a > b ? 1 : 0);
}
```

最终 comparator 还必须使用完整路径兜底，保证刷新前后结果稳定。

注意：界面虽然隐藏 `.md` / `.markdown` 扩展名，排序和消歧仍必须使用完整文件名。如果同一目录同时存在 `note.md` 与 `note.markdown`，界面应临时显示扩展名或在副标题、tooltip 中说明，避免出现两个完全相同的“note”。

#### 分层职责

| 层级 | 职责 |
|---|---|
| Rust | 安全读取文件系统并返回完整元数据，不决定用户展示偏好 |
| Zustand | 保存原始文件树和排序设置 |
| selector / utility | 递归生成排序后的派生树，不修改原始状态 |
| React | 渲染派生树，执行自动展开、滚动和选中 |

应删除 Rust 中“按修改时间倒序”作为唯一排序的逻辑。为测试和非 UI 调用需要，Rust 可以使用简单稳定顺序返回，但 UI 不得依赖操作系统 `read_dir` 顺序。

### 5.5 拖拽移动规范

#### 支持范围

第一阶段拖拽只表示“移动文件或文件夹到目录”，不表示手工排序。

有效放置目标：

- 文件夹行；
- 明确标识的工作区根目录空白区域。

无效目标：

- Markdown 文件行；
- 源项目自身；
- 源文件夹的后代目录；
- 已经所在的同一目录；
- 存在同名项目的目录。

#### 交互反馈

1. 拖动开始后为源项目增加半透明状态；
2. 只有真实目标文件夹行高亮，不高亮整个递归子树；
3. 高亮旁显示“移动到：目录名”；
4. 悬停折叠文件夹约 500–700ms 后自动展开；
5. 无效目标使用禁止光标和弱红色提示；
6. 拖放成功后选中并定位新路径；
7. 移动当前打开文档时保持编辑器内容和光标状态；
8. 移动文件夹时同步映射其内部当前文件、最近文件和展开路径。

#### 确认与撤销

推荐分阶段实施：

- 第一阶段没有撤销能力时，拖拽移动前显示简短确认；
- 第二阶段接入文件操作历史后，成功提示中提供“撤销”；
- 具备可靠撤销后，可以允许用户关闭拖拽确认。

不要只依赖 watcher 恢复 UI。移动成功后应以 Rust 返回的新路径为准更新状态，再由 watcher 做外部变更兜底。

## 6. 技术设计

### 6.1 新增模块建议

```text
src/
├── components/sidebar/
│   ├── Sidebar.tsx
│   ├── ExplorerToolbar.tsx
│   ├── FileTree.tsx
│   └── SortMenu.tsx
├── services/
│   ├── documentSession.ts
│   └── explorerOperations.ts
├── stores/
│   └── appStore.ts
└── lib/explorer/
    ├── createTarget.ts
    ├── sortFileTree.ts
    └── pathMapping.ts
```

核心原则：

- `Sidebar` 只编排交互，不继续堆积文件操作细节；
- 新建目标解析、排序和路径映射使用纯函数；
- 文件写入、移动和删除仍通过 `DesktopAPI` 调用 Rust；
- UI 不自行拼接未校验的最终写入路径。

### 6.2 建议类型

```ts
export type ExplorerSortMode = 'name' | 'modified' | 'type';
export type SortDirection = 'asc' | 'desc';

export interface ExplorerPreferences {
  sortMode: ExplorerSortMode;
  sortDirection: SortDirection;
}

export interface ExplorerSelection {
  path: string;
  kind: 'file' | 'folder';
}
```

建议默认值：

```ts
selectedEntry: null,
expandedPaths: [],
explorerSortMode: 'name',
explorerSortDirection: 'asc',
```

### 6.3 排序伪代码

```ts
function sortFileTree(nodes: FileNode[], preferences: ExplorerPreferences): FileNode[] {
  return nodes
    .map((node) => ({
      ...node,
      children: node.children
        ? sortFileTree(node.children, preferences)
        : undefined,
    }))
    .sort((a, b) => {
      if (a.type !== b.type) return a.type === 'folder' ? -1 : 1;

      const direction = preferences.sortDirection === 'asc' ? 1 : -1;
      const primary = compareByMode(a, b, preferences.sortMode);
      if (primary !== 0) return primary * direction;

      return compareNames(a.name, b.name)
        || compareRawName(a.name, b.name)
        || compareRawPath(a.path, b.path);
    });
}
```

修改时间模式要把无效时间放在末尾，不能让 `NaN` 破坏 comparator 的传递性。

### 6.4 自动定位

建议维护一个一次性请求：

```ts
type RevealRequest = {
  path: string;
  select: boolean;
  focus: boolean;
};
```

新建、移动或外部打开文件后：

1. 计算目标所有祖先路径；
2. 合并到 `expandedPaths`；
3. 等待树渲染；
4. 使用 `scrollIntoView({ block: 'nearest' })`；
5. 设置选择与焦点；
6. 消费并清除 reveal request。

## 7. 实施计划

### 阶段 1：排序稳定化（P0）

- 新增 `sortFileTree.ts`；
- 默认文件夹优先、名称自然升序；
- 增加名称、最近修改、类型三种模式；
- 排序设置持久化；
- 移除 Rust 修改时间作为唯一展示顺序的依赖；
- 增加 comparator 单元测试。

### 阶段 2：选择状态重构（P0）

- 增加 `selectedEntry`；
- 文件、文件夹均可选择；
- 点击空白和 Escape 取消选择；
- 取消选择不关闭文档；
- 重命名、删除快捷键优先作用于选择项；
- 为“已打开但未选中”的文件增加弱标识。

### 阶段 3：新建位置统一（P0）

## 9. 风险标记

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| `RISK-EXPLORER-STATE` | 高 | 直接用 `currentFile = null` 取消选择会关闭编辑器状态 | 必须先拆分 `selectedEntry` |
| `RISK-CREATE-TARGET` | 高 | 隐式目录规则会把文件创建到非预期位置 | 统一 resolver，弹窗展示目标路径 |
| `RISK-DND-DATA` | 高 | 拖拽移动属于真实文件系统变更 | 保留 Rust 守卫、冲突拒绝和保存协调 |
| `RISK-DND-UX` | 中 | 放置区过大会造成误移动 | 只允许文件夹行和根区域接收 |
| `RISK-SORT-FLICKER` | 中 | watcher 和前端同时排序可能造成短暂跳动 | 展示层使用单一纯 comparator |
| `RISK-COLLATION` | 中 | 不同系统语言环境可能得到不同名称顺序 | 使用系统 locale，并用原始名称、路径稳定消歧 |
| `RISK-UNDO-CONFLICT` | 中 | 撤销时目标路径可能已被占用 | 撤销前重新校验并提示冲突 |
| `RISK-PERFORMANCE` | 低 | 大型树每次渲染递归排序可能增加开销 | selector memoization，文件变更或排序设置变化时重算 |

## 10. 验收结论

本方案完成后的文件管理系统应满足：

1. 默认顺序稳定、符合“文件夹优先 + 自然名称排序”的通用认知；
2. 打开文档和选择文件树项目互不绑死；
3. 用户能够取消选择而不关闭当前文档；
4. 工具栏新建位置完全由可见选择决定，并在弹窗中明示；
5. 新建、移动后目标可见、可定位；
6. 拖拽只表达目录移动，目标明确且不允许模糊落点；
7. 底层工作区边界、保存协调和冲突拒绝继续生效；
8. 排序、选择、新建和移动均有可自动验证的规则，而不是依赖组件局部状态。

最终推荐默认策略：**文件夹优先、名称自然升序、打开自动定位；选择状态独立于编辑状态；新建位置由文件树选择决定；拖拽移动可确认并逐步支持撤销。**
